# Dataflix — Technical Implementation Plan (Databricks Free Edition)

## Context

The product doc (`/home/ubuntu/dataflix/dataflix-product-doc.md`) defines Dataflix: a multi-agent Genie system for streaming content strategy, with a Supervisor Agent orchestrating 7 Genie Spaces + a Document Agent + a multimodal tagging layer, plus 2 product features (Sources Used panel, Casting Recommendation). The user wants to actually build this for a hackathon, powered by Databricks Genie and Agent Bricks, on **Free Edition only**.

**Scope cut, 2026-08-23 (product decision):** Proactive Risk Digest, Renewal ROI Calculator, and Persona Switcher are cut entirely — see the product doc's "Cut from scope" note for why (duplicate renewal-verdict surfaces; Persona Switcher added no new capability). The offline anomaly-detection job (Section 4, old) is cut too since Risk Digest was its only consumer. `fact_competitive_catalog` as a *synthetic* table is also cut — Genie F (if built, Tier 4/stretch) queries `core.real_watch_providers` (already real) directly instead of inventing new competitor data.

**`dataflix-product-doc.md` is the standing source of truth for product scope — trimmed to business outcome, problem, personas/user stories, and core features (implementation detail lives only here in PLAN.md). Any agent implementing a piece of this plan must (re-)read `dataflix-product-doc.md` before making a feature-level decision — e.g. before writing Supervisor system instructions, wording Genie Space tool descriptions, or building a UI feature — so persona framing, the anchor question, and feature scope stay consistent with product intent rather than drifting from what's convenient to build.

Two things drove this plan's shape:

1. **Databricks Free Edition constraints are real and specific** (researched live, Aug 2026): a single 2X-Small serverless SQL warehouse (no scaling), Genie API capped at ~5 req/min (~20/min via UI), max 30 tables/Genie Space, one AI Search endpoint with one search unit, Jobs capped at 5 concurrent tasks. (Databricks Apps' documented "3/account" cap did **not** hold in practice — 3 apps coexist fine, actual ceiling is much higher.) Agent Bricks (Multi-Agent Supervisor, Knowledge Assistant) is officially documented as unsupported on Free Edition. **Confirmed split, 2026-08-23**: Multi-Agent Supervisor works (proven with real invocations); Knowledge Assistant does not (`HTTP 500` on query, UI confirms "Brick Type is not supported in Free Edition") — the cold-spare fallback this plan pre-planned for exactly this scenario was built and works (Section 3).
2. **Project is completely greenfield** — only the product doc exists locally. No Databricks CLI, no credentials, no code, no data. Everything below is new.
3. **The catalog is grounded in real movie/actor data, not fully synthetic titles.** Title metadata (name, genre, cast, poster art, release date) for both Hollywood and Bollywood content comes from **TMDB (The Movie Database)** via its free API, fetched once locally (outbound internet from Databricks Free Edition compute is restricted to trusted domains, so this happens outside the workspace, not in a Databricks Job) and uploaded as a static extract. This needs a free TMDB API key (themoviedb.org) as a prerequisite. Business metrics layered on top (engagement, licensing, support, marketing) remain synthetic — real streaming numbers aren't public — but are now keyed to real title_ids, which makes every downstream demo answer reference an actual recognizable film/show instead of a generated placeholder name. Competitive-availability data is the one exception: it's sourced from TMDB's real watch-provider data (`core.real_watch_providers`), not synthesized (see the scope-cut note above).

The user explicitly chose to attempt the **full architecture** (all 7 Genie Spaces + Document Agent + offline ML), accepting the risk of cutting scope mid-build if Free Edition limits bite — so this plan includes an explicit, prioritized cut-list rather than pre-trimming the scope.

**Agentic evaluation is a first-class, built-in component of this plan, not a pre-demo checklist item.** The product doc itself flagged "no eval story" as an open risk; this plan resolves it by wiring MLflow 3 GenAI evaluation into the Supervisor from Tier 0 onward and re-running it as a regression gate at every build tier (Section 6).

Relevant Databricks skills to load during implementation (not now, during build): `databricks:databricks-core` (CLI/auth first), `databricks:databricks-synthetic-data-gen`, `databricks:databricks-unstructured-pdf-generation`, `databricks:databricks-genie-agents`, `databricks:databricks-vector-search`, `databricks:databricks-agent-bricks`, `databricks:databricks-jobs`, `databricks:databricks-ml-training`, `databricks:databricks-apps` / `databricks-apps-python`, `databricks:databricks-unity-catalog`, `databricks:instrumenting-with-mlflow-tracing`, `databricks:databricks-mlflow-evaluation`.

## 3. Document Agent — **DONE, via cold-spare fallback (Knowledge Assistant confirmed broken on Free Edition, 2026-08-23)**

`notebooks/02_build_document_corpus_and_ocr.py`: extract text from digital docs directly (OCR/`/scanned_ocr` still deferred per Tier 0's scope cut). Chunked at ~375 words (~500 token approximation)/~40 word overlap into `dataflix.docs.doc_chunks(chunk_id, doc_id, doc_type, title_id, region_code, source_path, chunk_text, page_num)` — **377 rows across 40 docs** (30 synthetic contract PDFs generated per hero + sampled `fact_licensing` rows via `notebooks/02a_generate_synthetic_contracts.py` + the `databricks-unstructured-pdf-generation` skill's `plutoprint` converter, 10 real regulatory docs covering all 6 regions: US/MPA, India/CBFC×2, EU/AVMSD, UK/BBFC, Brazil×2 via `ai_translate()`, Japan/Eirin, **India/IAMAI OTT self-regulation code** — the last one being the real, OTT-specific streaming-industry code, more directly relevant than the theatrical CBFC rules, found via a legal-commentary site's tabular summary since IAMAI's own site doesn't have a stable public PDF link). Tracked in `doc_registry(doc_id, doc_type, is_scanned, source_type, source_path, ingested_at)`.

**Index**: `dataflix.docs.doc_chunks_index`, DELTA_SYNC (required `delta.enableChangeDataFeed=true` on `doc_chunks` first), embedding model `databricks-gte-large-en`, on the **existing** `summit_lens_vs` endpoint (reused, not a new one — Free Edition's one-search-unit cap means a second endpoint likely wasn't available; adding an index to an existing endpoint worked fine). Triggered pipeline. 212/212 rows indexed, retrieval quality-checked directly (`w.vector_search_indexes.query_index`) before wiring anything on top.

**Knowledge Assistant — attempted, confirmed non-functional.** Created successfully via CLI (`create-knowledge-assistant` + `create-knowledge-source`), reported `state: ACTIVE` and serving endpoint `state: READY`, but actually querying it returned `HTTP 500 Internal error`, and the Databricks UI separately surfaced "Knowledge Assistant Brick Type is not supported in Free Edition." This is the exact risk Section 9 flagged in advance (Multi-Agent Supervisor works fine — proven with real invocations — but Knowledge Assistant specifically does not on this workspace). Deleted the broken KA rather than leaving dead infrastructure around.

**Non-English real documents — use `ai_translate()`, not manual/LLM-authored translation.** Two of the real regulatory PDFs (Brazil's Ministry of Justice originals) are entirely in Portuguese, mismatched against the English-only embedding model (`databricks-gte-large-en`). First pass used a manually-authored English summary (real facts, human-written container) — corrected on request to a genuinely Databricks-native pipeline instead: extract PDF text page-by-page → stage as a Delta table (`doc_name, page_num, pt_text`) → `SELECT ai_translate(pt_text, 'en') FROM ...` (one SQL AI Function call per page, 87 pages in one batch) → reassemble into English PDFs (`brazil_portaria_502_en.pdf`, `brazil_guia_pratico_en.pdf`) → same chunk/index pipeline as everything else. Verified equivalent retrieval quality to the manual version. **Lesson**: prefer `ai_translate()`/AI Functions over ad-hoc LLM-authored translation whenever the source is non-English — traceable, reproducible, and a genuine platform capability rather than an opaque one-off.

**Fallback used instead of Knowledge Assistant (the pre-planned cold-spare, but faster than the ~2-3h estimate since it's SQL, not a hand-rolled Python orchestration loop):** Databricks SQL's native `VECTOR_SEARCH()` table function queries the index directly and works from a plain SQL warehouse — no Agent Bricks involved. Wrapped it in a UC SQL function:
```sql
CREATE FUNCTION dataflix.docs.search_documents(
  search_query STRING COMMENT 'Natural language search query',
  region_filter STRING DEFAULT NULL COMMENT 'Optional region code to filter to'
)
RETURNS TABLE (chunk_id STRING, doc_type STRING, title_id STRING, region_code STRING, chunk_text STRING, page_num INT)
RETURN
  SELECT chunk_id, doc_type, title_id, region_code, chunk_text, page_num
  FROM VECTOR_SEARCH(index => 'dataflix.docs.doc_chunks_index', query => search_query, num_results => 5)
  WHERE region_filter IS NULL OR region_code = region_filter
```
Registered as a Supervisor tool via `tool_type: uc_function` (a native, fully-supported tool type — no Knowledge Assistant required). The Supervisor calls it, gets raw chunks back, and does its own synthesis/citation — which it's already good at (proven in Section 6's eval). **Verified**: the full literal anchor question (engagement + licensing + rating/compliance) now works end-to-end in one call, correctly retrieving real CBFC/regulatory text and correctly surfacing the cost-efficiency tension per the Section 5 instructions.

**Known gap, quick follow-up**: `core.dim_title_certification` (real per-title ratings, Section 1) isn't wired into any tool yet, so the Supervisor can't yet answer "what is Title X's exact certification" — it only has the general regulatory *guidelines* via `search_documents`, not the specific real rating. Fixing this is the prerequisite for the Compliance Risk Scanner deferred idea: either add it to a Genie Space (e.g., Space B) as a joinable table, or expose it via another UC function.

**Inline poster rendering in chat — DONE (2026-08-23):** `poster_signals.poster_url` added (`https://image.tmdb.org/t/p/w500{poster_path}`, real live TMDB CDN, verified reachable) via `MERGE` from `dim_title.poster_path`. Streamlit needed no code change (`st.markdown` already renders markdown images). Next.js needed `react-markdown` added and `page.js` updated to render assistant messages through it.

**Size/inline fix (2026-08-23, follow-up):** `poster_url` switched from TMDB's `w500` size to `w185` (a real, smaller TMDB CDN variant, not CSS-scaled from a bigger file) so it's thumbnail-sized by default everywhere. Next.js's `img` styling also changed from `maxWidth:100%`/`display:block` (full-width block image) to a fixed `width: 90px`, `display: inline-block` so it sits alongside/near text rather than dominating its own full-width line. The local full-res poster JPGs used for vision tagging (Section 4's FM call) are unaffected -- only the URL surfaced for chat display changed.

**Streaming answers (Next.js only, 2026-08-23):** the Supervisor endpoint supports `"stream": true` and emits a Responses-API-shaped SSE stream. Confirmed empirically: `response.output_text.delta` events carry real token-by-token model output (both intermediate narration and the final answer, keyed by `item_id`/`step`); `response.output_item.done` fires for every item but for text messages it's a redundant full-text echo of what deltas already sent -- the ONE place `.done` carries new information is `function_call` items, which have no preceding deltas at all (harness-injected, not model-generated), same as the `<name>tool</name>` marker messages and raw tool-result-table dumps. `route.js` now proxies the upstream SSE into a simpler protocol (`{type:"text",delta}` / `{type:"tool_call",name}` / `{type:"done"}`), dropping the marker/table noise but keeping a live `*checking {tool}...*` status line on each tool call. `page.js` consumes this via `response.body.getReader()`, appending deltas to the last message in place (with a blinking `▍` cursor while streaming) instead of waiting for one buffered JSON response. This does NOT reduce total wall-clock time (still ~20-65s of real work) but makes it feel dramatically faster since the user sees continuous live progress instead of a blank spinner -- and it's compute-neutral, no extra warehouse/FM load. - **Source-citation PDF highlighting — PENDING, expanded spec added to plan 2026-08-23, not started:** when the Document Agent answers a question by citing a licensing contract or compliance PDF, generate a version of that PDF with the SPECIFIC points relevant to that exact business question highlighted -- not just "this chunk was retrieved," but the actual sentences/clauses within it that answer what was asked, so a compliance/legal reviewer can visually verify the answer instead of trusting a chatbot's prose summary. Concrete build plan:
  1. **Databricks-native layer**: `ai_parse_document()` (confirmed available on this workspace) returns structured layout output per page including per-element bounding boxes, not just extracted text -- this is the mechanism that makes pixel-accurate highlighting possible instead of a generic "see page 3" pointer.
  2. **Query-driven relevance, not blanket chunk-highlighting**: given the retrieved chunk's text AND the user's actual question, one FM call identifies which specific spans within that chunk actually answer the question (e.g. for "does this contract cover exclusivity in India?", highlight only the exclusivity clause + India territory clause, not the whole retrieved paragraph) -- then map those spans back to `ai_parse_document`'s bounding boxes for that page.
  3. **Render**: draw highlight rectangles at those bounding-box coordinates onto the source PDF page (e.g. via `pypdf`/`reportlab` overlay, consistent with the project's existing PDF-generation tooling) and save a per-question, per-document highlighted PDF (or per-page image export for the carousel below).

PDFs would need to be served the same way thumbnail images are (static assets or a dedicated API route from a UC Volume), not embedded as base64 in chat text.
  5. Not started -- no `ai_parse_document` call has been made yet in this project, and no PDF-serving mechanism exists yet (only images are currently served as static assets). This is a genuinely new build, not an extension of an existing pipeline.
